# Agent guide

Chess Chaos Lab is a Rust 2024 workspace. `crates/chess-core` owns legal game state, clocks, FEN/PGN and save data; `crates/chess-ai` owns local move selection; `crates/chess-uci` owns subprocess protocol; `apps/chess-chaos-lab` owns the native UI and autosave. Keep those boundaries intact. `docs/` is the source for published documentation.

Use stable Rust with the Windows MSVC toolchain for the verified target. Before merging, run `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, and `cargo test --workspace --locked`; run `cargo build --release --locked` for release-related changes. Build the site with `npm ci --prefix site` and `npm run build --prefix site` when docs or site change. Add a focused regression test for a significant bug. Never change expected results merely to silence a failure.

Prefer clear names and small functions over explanatory comments. Comments should explain a non-obvious chess rule, invariant, UCI detail, compatibility constraint, unsafe assumption, or performance trade-off; keep them current. Public interfaces need useful rustdoc. Use idiomatic Rust, `Result` for recoverable errors, and no unreviewed `unsafe`. Do not ignore failures, crash on untrusted data, allocate unnecessarily in hot paths, put rules in the UI, or block rendering with engine I/O.

Make focused Conventional Commits, stage explicit paths, inspect staged diffs, and use a branch and pull request after the baseline. Do not force-push, bypass required checks, expose secrets, bundle an external engine, publish crates, or alter the license without a specific decision. Normal builds and docs edits do not create releases. A release requires a reviewed version/tag, green CI, a checked Windows package and checksum, and a reviewed draft release; see [release policy](docs/release.md). Check [feature matrix](docs/feature-matrix.md), [roadmap](docs/ROADMAP.md), and [known limitations](docs/known-limitations.md) before claiming completion.
